## Critical — results integrity

### C1. ✅ Crashed/errored games are recorded as 1/2-1/2 draws (HIGH) — **FIXED 2026-08-07**
*Fix: `ParallelExecution.fs` now skips replay-seeding, PGN write, and the results bag for `Reason = Cancel`; the round-robin path in `TournamentRunners.fs` got the same `isCancelled` guard the cup path already had (the phantom `Result.Empty` issue in Cup/Swiss/Ladder state is a separate medium finding, not covered by this fix).*
`ChessLibrary/Tournament/GameHelpers.fs:70-71, 135-197` + `ChessLibrary/Tournament/ParallelExecution.fs:450` + `ChessLibrary/Tournament/GamePersistence.fs:93-102`

`handleGameException` maps "both engines crashed", "unresolved pipe error", and "unexpected exception, both alive" to `createCancelResult()` = `"1/2-1/2"` with `Reason = Cancel`. The parallel-console writer gates only on `cts.IsCancellationRequested` (not on `Reason`) before posting `WriteGame`; GUI RoundRobin has the same hole via `writeGameToPgnSimple` (`TournamentRunners.fs:279`) — unlike `writeGameToPgn`, it does not exclude `Reason = Cancel`. No filter on `Reason = Cancel` exists anywhere in `ChessLibrary/Analysis`.

**Impact:** a mid-game exception (feed parse bug, transient IO) with no user cancellation becomes a phantom draw permanently in the PGN, counted by standings/pentanomial/SPRT — and `Scheduler.Diff.diff` counts the pair as played on resume, so the real game is never replayed. Directly threatens tuning and net-testing results.

### C2. ✅ Console tournaments always run with `PreventMoveDeviation = true` (HIGH) — **FIXED 2026-08-07**
*Fix: `tournament.TestOptions` → `tourny.TestOptions` in `Console/Program.fs`.*
`Console/Program.fs:2306`

```fsharp
tournament <-
    {tourny with
        EngineSetup = engineSetup
        PreventMoveDeviation = tournament.TestOptions.NumberOfGamesInParallelConsoleOnly <= 1
```
`tournament` is still the mutable `Tournament.Empty` placeholder at this point (it is only assigned by this very expression); `Empty` has `NumberOfGamesInParallelConsoleOnly = 1` (`CoreTypes.fs:910`), so the condition is unconditionally true. Should be `tourny.TestOptions...`.

**Impact:** any `tournamentjson` run with parallelism > 1 silently gets move-replay logic enabled in parallel runs — the combination the codebase deliberately avoids elsewhere (`runPvBatch` clamps concurrency to 1 *because* it enables PreventMoveDeviation).

### C3. ✅ Winboard evals have the wrong sign whenever Black is to move (HIGH) — **WONTFIX (user decision 2026-08-07)**
*User has tested Winboard engines and they deliver correct evals in practice; the translation layer is deliberately left untouched.*
`ChessLibrary/Engine/WinboardProtocol.fs:160-191` (`parseThinkingOutput`), `:197-219` (`parseCometTellics`)

The handler normalizes scores to **White's** perspective on the stated premise "UCI standard: scores from White's perspective" (line 164). That premise is wrong — UCI scores are side-to-move perspective, and every downstream consumer assumes so: `EngineProtocol.Regex.getEssentialData[WithEPS]` does `if isWhite then eval/100.0 else -eval/100.0` (`EngineProtocol.fs:349-351`); `GameHelpers.fs:243` passes `not isWhite` for pondering engines for the same reason.

**Impact:** a Winboard engine thinking as Black gets its already-White-POV score negated again — inverting every eval it reports; corrupts GUI display and eval-agreement draw/win adjudication. `parseCometTellics` emits the raw score with no perspective handling (same problem on one side).

### C4. ✅ PGN parser: module-level mutable state + variation color desync (HIGH) — **FIXED 2026-08-07**
*Fix: all parse state moved into a per-parse `ParserState` record created inside each `seq { }` (concurrent parses and re-enumerations are now fully independent); variation `(` `)` now saves/restores the color toggle and uses the parent move's ply, so a variation's first move carries the replaced move's color and ply. Regression tests added in `TestProject/ParserTests.fs`. The movetext `1-0`/`1/2-1/2` result-token gap and multi-line comment handling are separate medium findings, still open.*
`ChessLibrary/Parsing/FullPGNParser.fs`

- **`:17-52` — global mutable parse state.** All header/move state is `let mutable private` at module scope, but `parsePgnFile`/`parsePgnString` are called concurrently from ~17 WebGUI pages (Blazor Server threads), tournament workers, and the SPRT callback's `GetPGNGames()`. Two overlapping parses interleave into merged/garbled games with no error. The returned `seq` is also lazy over this shared state: `PGNWriter.writeOpeningPgnFile` (`:173/178/188`) enumerates its input three times — with a parser seq the second enumeration starts from stale state (`gameNumber` keeps incrementing, no `resetState`).
  Concrete scenario: Speed Calculator open on the live tournament PGN while the SPRT callback runs → both results silently wrong.
- **`:264-289, :346-364, :398-415` — variation color/ply corruption.** The `whiteSan`/`blackSan` toggle is not saved/restored across `(` `)`. A variation on a white move starts with the toggle still set → its first move is labeled `"b"`; an odd-length variation flips the color of every subsequent **mainline** move. Also `currentPly <- parentPly + 1` (`:279`) gives the variation's first move the ply *after* the move it replaces. Downstream, `PGNExtractor.extractEngineStats` attributes stats by `move.Color` and `PGNWriter` emits move numbers by color → stats mis-attributed and broken re-serialization for any annotated PGN with variations. Existing ParserTests never assert `Color`, so they pass.

## Crashes and hangs

### H1. ✅ Engine that dies during startup hangs the constructor for 2 hours, then leaks the process (HIGH) — **WONTFIX (user decision 2026-08-07)**
*The long startup wait is intentional; left untouched.*
`ChessLibrary/Engine/Engine.fs:152-168` (+ `:586-589, :623-626`)

`waitForInitialization` polls only `inUciResponsMode`/`inIsreadyMode` and the token — never `engineProcess.HasExited`. Timeout is `TimeSpan.FromHours(2)`. `write` (`:367-369`) doesn't throw for an exited process. An lc0/Ceres with bad backend/missing DLL exits ms after start, "uciok" never arrives, and the `ChessEngineWithUCIProcessing` constructor (used by `createAltEngine` for every analysis-page engine) blocks the calling thread for 2 hours. If alive-but-wedged, the eventual `failwith` leaves the process running with no `Kill` — no dispose path other than a successful `Quit`. Contrast: `ChessEngine.readUciOptions` handles this correctly (120s timeout + null-read → false).

### H2. ✅ `moveBoard` raced between command thread and stdout reader thread (HIGH) — **FIXED 2026-08-07**
*Fix: new `moveBoardLock` in `ChessEngineWithUCIProcessing`; all `moveBoard` access goes through it — the reader thread's `bestLine` snapshot / `regular` STM read / SAN PV conversion / `makeShortSan`, and the command thread's `Position`/`PositionWithMoves` mutations plus `CurrentPositionCommand()`. A position set now waits for the line being parsed instead of mutating the board underneath it. Callbacks are invoked outside the lock; `sanPvCache` stays reader-thread-only as before. Verified via analyze CLI smoke test with Stockfish.*
`ChessLibrary/Engine/Engine.fs:766-787` vs `:173-265`

`SendUCICommand (Position/PositionWithMoves)` runs `moveBoard.ResetBoardState()`/`LoadFen`/`PlayCommands` on the caller's thread while the `OutputDataReceived` thread reads the same board in `regular` and `bestLine`. Routinely exercised: `AnalysisManager.SearchNodes/GoInfinite` (`AnalysisManager.fs:70-103`) send `Stop` then immediately reposition without waiting for the stopped search's trailing info/bestmove lines. The `sanPvCache` comments (`:84-86, :294-296`) show the hazard was known for the cache but the Board got no protection. Consequences: garbage SAN PVs, `BestMove` records with wrong FEN, spurious "illegal move" reports, silently-absorbed exceptions.

### H3. ✅ Game Review "Review All" throws NRE after the first game (HIGH) — **FIXED 2026-08-07**
*Fix: separate loop-level `reviewAllCts` — the loop no longer reads the per-game `analysisCts` that `StartAnalysis` disposes/nulls in its `finally`. Cancel now cancels both (previously it only skipped the current game during Review All); DisposeAsync cleans up both.*
`WebGUI/Components/Pages/AnalysisPages/GameReview.razor:594` vs `:899-900`

`StartAnalysis`'s `finally` does `analysisCts?.Dispose(); analysisCts = null;`. `ReviewAllGames` re-reads the field each iteration (`analysisCts.Token.IsCancellationRequested`) → NRE on iteration 2; games 2..n never reviewed.

### H4. ✅ PlayVsComputer: engine bestmove mutates the shared board on the reader thread; async void can kill the process (HIGH) — **FIXED 2026-08-07**
*Fix: `HandleEngineUpdate` now mirrors EnginePanel — non-async wrapper marshals via `InvokeAsync` to `HandleEngineUpdateCore`, guarded by a new `disposeCts` (cancelled in DisposeAsync) with a catch-all so no exception escapes into async void. Board mutation now always happens on the dispatcher.*
`WebGUI/Components/Pages/PlayVsComputer.razor:939-958, :862-896`

`SimpleEngineAnalyzer` invokes its callback directly on the engine reader thread (`AnalysisManager.fs:15`). EnginePanel and KibitzerPanel were fixed to marshal (v1.5.2), but PlayVsComputer's `HandleEngineUpdate` was not: `OnEngineMoveReady` does `board.PlayUciMove(...)` and reads `board.MovesAndFenPlayed` off-dispatcher while ModernChessboard renders the same board — the known "Collection was modified" crash class. `HandleEngineUpdate` is `async void` with **no** try/catch and no `disposeCts` guard: (a) any exception after the first await is unhandled on a no-sync-context thread → kills the **process**; (b) a bestmove after `DisposeAsync` still plays a move on the dead page's board. Fix shape: mirror EnginePanel (`InvokeAsync` + dispose CTS + catch-all).

### H5. Tournaments.razor `Update`: async void on a non-UI thread with a too-narrow exception filter (MEDIUM) — **FIXED 2026-08-07**
*Fix: added a general catch-all with logging after the TCE/ODE filter in `Update`, and wrapped `CancelTournament`'s body in try/catch — no exception can escape either async void into the process anymore.*
`WebGUI/Components/Pages/TournamentPages/Tournaments.razor:1564, :2064-2068`

`TournamentService.HandleUpdate` invokes the subscriber on the tournament worker thread; `Update`'s only guard is `catch (Exception ex) when (ex is TaskCanceledException or ObjectDisposedException)`. Any other exception after the first await (e.g. `JSDisconnectedException` from the between-games dialog after a tab closed) escapes the async void and terminates the server process. `CancelTournament` (`:1335-1344`) is also async void with no try/catch and is called fire-and-forget from inside `Update` (`:1842`).
